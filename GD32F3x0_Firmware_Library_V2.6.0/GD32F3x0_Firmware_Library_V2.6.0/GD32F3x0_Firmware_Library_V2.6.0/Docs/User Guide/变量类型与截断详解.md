# C 变量类型、数值范围与截断

> 本文档聚焦两个问题：
> 1. **变量类型截断**（本次 OTA F1 问题的真正根因）：常用整数类型的数值范围、二进制表达，以及截断原理。
> 2. **DMA 单次模式地址重置**的再审视：原论断有误，予以澄清。

---

## 一、常用整数类型：数值范围与二进制表达

### 1.1 类型总表

| 类型 | 位数 | 有符号范围 | 无符号范围 | 十六进制表示 | 最大二进制 |
|---|---|---|---|---|---|
| `uint8_t` | 8 | — | 0 ~ **255** | 0x00 ~ 0xFF | `1111_1111` |
| `int8_t` | 8 | -128 ~ 127 | — | 0x80 ~ 0x7F | — |
| `uint16_t` | 16 | — | 0 ~ **65535** | 0x0000 ~ 0xFFFF | `1111_1111_1111_1111` |
| `int16_t` | 16 | -32768 ~ 32767 | — | 0x8000 ~ 0x7FFF | — |
| `uint32_t` | 32 | — | 0 ~ **4294967295** | 0x00000000 ~ 0xFFFFFFFF | 32 个 1 |
| `int32_t` | 32 | -2147483648 ~ 2147483647 | — | 0x80000000 ~ 0x7FFFFFFF | — |

### 1.2 二进制表达示例

- **255**（uint8_t 上限）= 0xFF = `1111_1111`（8 位全 1）
- **256** = 0x100 = `1_0000_0000`（需要 **9 位**，uint8_t 装不下）
- **518** = 0x0206 = `0000_0010_0000_0110`（16 位）
- **65535**（uint16_t 上限）= 0xFFFF = `1111_1111_1111_1111`
- **65536** = 0x10000 = `1_0000_0000_0000_0000`（需要 **17 位**，uint16_t 装不下）

> 关键记忆点：**每种无符号类型能装的最大值 = 2^位数 - 1**。装不下的值，其"多余的高位"会被丢弃（截断）。

## 二、变量类型截断（主问题）

### 2.1 截断是什么

C 语言里，把一个**大类型的值**赋给**小类型变量**、或作为参数传给**更窄的参数**时，编译器只保留**低 N 位**、丢弃高位——**不报错**（隐式收窄）。

```
518 = 0x0206 = 0000_0010_0000_0110   (uint16_t，2 字节)
                 └── 高 8 位 ──┘└─ 低 8 位 ─┘
塞进 uint8_t（只留低 8 位）→       0000_0110   = 0x06 = 6
```

**518 塞进 uint8_t → 6。**

### 2.2 本次实际案例

```
解析器：idx=518 expect=518 func=F1   ← 解析完全正确，凑满了 518 字节
调用：  ota_handle_write(parse_buf, 518)
函数签名：void ota_handle_write(uint8_t *frame, uint8_t len)
                                            ↑ len 是 uint8_t
入参：518 = 0x0206 → 截断成 uint8_t = 6
→ if (len < 518) → 6 < 518 → 永远 "frame length too short"
```

**这就是 OTA F1 一直"too short"的根因**：不是接收、不是解析，而是 `len` 参数用了 `uint8_t`，装不下 518。

### 2.3 怎么判断会不会被截断

| 目标类型 | 安全上限 | 超出就截断 |
|---|---|---|
| `uint8_t` | 255 | 256、518、1000… |
| `uint16_t` | 65535 | 65536、70000… |
| `uint32_t` | 4294967295 | 一般不会 |

**凡是帧长、长度、计数器、数组下标等可能超过 255 的值，一律用 `uint16_t`（或更大）**，不要用 `uint8_t`。

### 2.4 避免截断的要点

1. **函数参数**：可能装大值的参数用 `uint16_t`/`uint32_t`，别图省事用 `uint8_t`。
2. **局部变量/结构体字段**：类型要和实际取值范围匹配。
3. **传参留意隐式转换**：`uint16_t 518` 传给 `uint8_t` 参数是静默截断，编译器不提示。

## 三、DMA 单次模式地址重置的再审视

### 3.1 原论断

- 曾推断：DMA 单次模式收完一帧后，内存地址寄存器（DMA_CHMADDR）前移；ISR 重配只重置计数、不重置地址 → 第二帧写到错误偏移 → 解析到脏数据。
- 据此在 ISR 里加了 `dma_memory_address_config(DMA_CH2, usart0_rx_buffer)`。

### 3.2 反证（实践观察）

- **communicate_protocol 业务协议**（0x82 → 0x84 等）**连续发送两个不同功能码，从未出现"第二个命令识别不了"**。
- 若 DMA 地址真不重置：第二帧（0x84）会写到 `buffer[5]` 起，主循环读 `buffer[0..4]` 仍是上一条 0x82 → 设备应回复错误的旧命令。但实际**每次都正确识别**。
- **结论：DMA 内存地址在重使能时会被重置**（或该问题在硬件上不成立），"地址没重置导致第二帧错位"的论断**不成立**。

### 3.3 为什么 F1 曾"加地址重置后才有回复"

- 该现象与**重新编译了 F1 定长 518 解析器**、缓冲区宏收口等改动**同时发生**，被时间混淆。
- 用调试打印逐段定位后，**真正、且唯一被证实的原因**是 `uint8_t len` 截断（`parse idx=518 expect=518`，但 `ota_write len=6`）。
- 所以：`dma_memory_address_config` 是**无害的正确写法**（把地址重设到基址永远安全），但**它不是 F1 问题的根因**。

### 3.4 小结

| 项 | 结论 |
|---|---|
| DMA 地址重置是根因吗 | **否**。业务协议连续不同功能码正常即反证 |
| `dma_memory_address_config` 该不该留 | 可留（无害、稳妥）；也可去掉，均不影响功能 |
| 真正的根因 | **`uint8_t` 参数截断**（518→6） |

---

## 四、一句话总结

**主问题 = 变量类型截断**：值超过 255 却用 `uint8_t` 存/传，高位被静默丢弃（518→6），表现为"逻辑上不可能"的怪现象。判断和预防就一条：**可能超 255 的长度一律 `uint16_t`**。
