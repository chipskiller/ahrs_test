# GD32F3x0 OTA 固件升级系统使用手册

## 1. 系统概述

本系统实现了基于串口的 **OTA（Over-The-Air）固件升级**功能，支持通过串口远程更新 GD32F3x0 芯片上的固件，无需使用 JLink/STLink 编程器。

系统由三部分组成：

- **Bootloader**（`bootloader_main.c`）：上电后首先运行，负责检测升级标志并安装新固件
- **OTA 协议层**（`ota_protocol.c/h`）：解析上位机下发的升级命令，管理 Flash 读写
- **Python 测试脚本**（`ota_test.py`）：上位机端工具，负责固件分包发送与进度显示

## 2. Flash 分区布局

```
┌─────────────────────────────────────────────────────────────┐
│ 0x08000000 - 0x08001BFF  Bootloader 代码区                   │
│ 0x08001C00              ★ 升级标志 (16B)                     │
│ 0x08001C10 - 0x08001FFF  Bootloader 空闲区                   │
├─────────────────────────────────────────────────────────────┤
│ 0x08002000 - 0x08008BFF  App 运行区 (27KB) ← 当前运行的固件  │
├─────────────────────────────────────────────────────────────┤
│ 0x08008C00 - 0x0800F7FF  下载区 (27KB) ← OTA 临时存放新固件  │
├─────────────────────────────────────────────────────────────┤
│ 0x0800F800 - 0x0800FFFF  数据分区 (2KB) ← Yaw/报警/零点等    │
└─────────────────────────────────────────────────────────────┘
```

> **关键设计**：OTA 升级时**只擦除 App 运行区**，数据分区绝对安全。升级标志存储在 Bootloader 区（`0x08001C00`），Bootloader 启动时读取此地址判断是否有待安装的固件。

## 3. 通信协议详解

### 3.1 帧格式

| 类型 | 帧格式 | 说明 |
|------|--------|------|
| **请求帧**（上位机→设备） | `[0xAA] [帧长] [功能码] [数据...] [校验码]` | 帧头固定 `0xAA` |
| **回复帧**（设备→上位机） | `[0x55] [帧长] [功能码] [数据...] [状态] [校验码]` | 帧头固定 `0x55`，状态码在数据**之后** |

> **帧长定义**：帧长 = 功能码(1B) + 数据(NB) + 校验码(1B) 的总字节数，**不包含帧头和帧长字节本身**。

### 3.2 校验算法

- **帧校验码**：从帧长字节开始，到校验码前的所有字节，逐字节 XOR，最后**取反**（`~xor_val`）
- **总包校验码**：所有数据包的数据区逐字节 XOR 累积（1 字节），**不取反**

### 3.3 四种命令帧

| 命令 | 功能码 | 帧格式 | 帧长 | 总帧长 |
|------|--------|--------|------|--------|
| 查询版本 | `0xF3` | `[AA][02][F3][CS]` | 0x02 | 4B |
| 开始升级 | `0xF0` | `[AA][14][F0][包数2B][版本16B][CS]` | 0x14 | 22B |
| 写入数据 | `0xF1` | `[AA][00][F1][包号2B][512B数据][CS]` | 0x00 | 518B |
| 结束升级 | `0xF2` | `[AA][03][F2][总校验码1B][CS]` | 0x03 | 5B |

> **写入帧特殊处理**：写入命令（0xF1）实际帧长 516B，超出单字节帧长范围（最大 255），帧长字段固定填 `0x00`。C 代码解析器检测到 `0xF1` 功能码后固定等待 518 字节。

### 3.4 回复帧状态码

| 状态码 | 含义 | 常见原因 |
|--------|------|---------|
| `0x00` (OK) | 操作成功 | — |
| `0x01` (FAIL) | 操作失败 | 包号不连续、校验不通过、Flash 写入失败 |

## 4. 完整升级流程

```
上位机                              设备 (App)                    Bootloader
  │                                    │                              │
  │── 0xF3 查询版本 ──────────────────>│                              │
  │<── 回复当前版本号 ─────────────────│                              │
  │                                    │                              │
  │── 0xF0 开始升级 (包数+版本) ──────>│                              │
  │                                    │── 擦除下载区 Flash            │
  │<── OK ─────────────────────────────│                              │
  │                                    │                              │
  │── 0xF1 写入数据 (包号+512B) ──────>│  (重复 N 次)                 │
  │                                    │── 写入 Flash + 回读校验       │
  │<── OK ─────────────────────────────│                              │
  │                                    │                              │
  │── 0xF2 结束升级 (总校验码) ────────>│                              │
  │                                    │── 校验总校验码                │
  │                                    │── 写升级标志到 0x08001C00     │
  │<── OK ─────────────────────────────│                              │
  │                                    │                              │
  │          ═══ 设备断电重新上电 ═══   │                              │
  │                                    │                              │
  │                                    │              ┌───────────────│
  │                                    │              │ 检测升级标志   │
  │                                    │              │ 擦除 App 区    │
  │                                    │              │ 下载区→App 区  │
  │                                    │              │ 清除升级标志   │
  │                                    │              │ 跳转新固件     │
  │                                    │              └───────────────│
```

## 5. Python 测试脚本使用

### 5.1 环境准备

```bash
pip install pyserial
```

### 5.2 命令行参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--port` | 串口号（如 COM3、/dev/ttyUSB0） | —（必填） |
| `--baud` | 波特率 | 9600 |
| `--firmware` | bin 固件文件路径 | — |
| `--version` | 目标版本号（ASCII，最长 16 字节） | AHRS_V2.0.0_2026 |
| `--version-only` | 仅查询设备当前版本，不升级 | — |
| `--test-frame` | 运行帧构造单元测试（无需串口） | — |
| `--raw` | 原始监听模式，显示所有串口数据 | — |
| `--raw-send` | 在 raw 模式下发送十六进制数据 | — |

### 5.3 常用操作示例

**查询设备版本：**

```bash
python ota_test.py --port COM3 --baud 9600 --version-only
```

**执行 OTA 升级：**

```bash
python ota_test.py --port COM3 --baud 9600 \
  --firmware "C:\path\to\app.bin" \
  --version AHRS_V2.0.0_2026
```

**运行帧格式单元测试：**

```bash
python ota_test.py --test-frame
```

**原始监听模式（调试用）：**

```bash
# 监听设备自发输出
python ota_test.py --port COM3 --baud 9600 --raw

# 发送指定帧并监听回复
python ota_test.py --port COM3 --baud 9600 --raw --raw-send "AA02F30E"
```

### 5.4 实时设备输出

升级过程中，脚本会自动捕获设备的 `printf` 调试输出，以 `[DEV]` 标签实时显示：

```

  [DEV] [OTA] writing flag: magic=0xAA55AA55 packets=52 cs=0x1E
  [DEV] [OTA] flag addr=0x08001C00
  [DEV] [OTA] erase done
  [DEV] [OTA] prog magic done
  [DEV] [OTA] verify: magic=0xAA55AA55 packets=52
11:53:53 [INFO] 升级完成！设备将重启安装新固件
```

## 6. Bootloader 工作流程

```
设备上电
  │
  ▼
Bootloader 启动 → 初始化串口 9600bps
  │
  ▼
读取 0x08001C00 的 magic
  │
  ├─ magic == 0xAA55AA55 ──→ 加载 total_packets
  │                            │
  │                            ▼
  │                          擦除 App 区 (0x08002000-0x08008BFF)
  │                            │
  │                            ▼
  │                          从下载区复制固件到 App 区
  │                            │
  │                            ▼
  │                          清除升级标志 (擦除 0x08001C00 页)
  │                            │
  │                            ▼
  ├──────────────────────────→ App 区有效？
  │                            │
  │                    ┌───────┴───────┐
  │                   是              否
  │                    │               │
  │                    ▼               ▼
  │              跳转到 App      进入 OTA 等待模式
  │                              (主循环解析串口数据)
```

> **升级标志结构（16 字节）**：`ota_flag_t` 包含 4 个 `uint32_t` 字段：`magic`（0xAA55AA55）、`total_checksum`、`total_packets`、`reserved`。Bootloader 读取 `total_packets` 计算复制大小。

## 7. 编译与烧录指南

### 7.1 首次烧录（使用编程器）

1. 在 Keil5 中编译 **Bootloader 项目**，生成 `bootloader.bin`
2. 在 Keil5 中编译 **App 项目**，生成 `app.bin`
3. 用 JLink/STLink 将 `bootloader.bin` 烧到 `0x08000000`
4. 用 JLink/STLink 将 `app.bin` 烧到 `0x08002000`
5. 设备上电，确认串口输出正常

### 7.2 OTA 升级后重新编译

修改 `ota_protocol.c` 或 `ota_protocol.h` 后，需要**同时重新编译 Bootloader 和 App 两个项目**，因为它们共用同一份协议代码。

> **常见遗漏**：修改了 `ota_protocol.c/h` 后只重新编译了 App 而忘记重新编译 Bootloader，会导致升级标志地址、解析逻辑等不一致，升级必然失败。

## 8. 调试技巧

### 8.1 串口 printf 噪声过滤

设备在 OTA 过程中会通过同一个串口输出 `printf` 调试信息，这些噪声字节会混在协议帧中。Python 脚本采用**全缓冲流式解析**：

1. 所有串口数据先存入 `bytearray` 缓冲区
2. 在缓冲区中搜索帧头 `0x55`
3. 检查帧长合理性（3~22 字节）
4. 校验码验证（XOR + 取反）
5. 功能码匹配验证
6. 任何一步失败只跳过 1 字节，其余数据保留继续搜索

### 8.2 Flash 写入回读验证

GD32 的 `fmc_word_program()` API 对超出芯片实际 Flash 容量的地址**不会报错**，但数据不会写入。关键操作后必须**回读验证**：

```c
// 写入升级标志后回读验证
fmc_word_program(OTA_FLAG_ADDR, flag.magic);
uint32_t verify = *((volatile uint32_t *)OTA_FLAG_ADDR);
if (verify != OTA_FLAG_MAGIC) {
    printf("*** FLAG WRITE FAILED! ***\r\n");
}
```

### 8.3 原始监听模式

当不确定设备是否正常响应时，使用 `--raw` 模式查看串口上的所有原始数据：

```bash
python ota_test.py --port COM3 --baud 9600 --raw
```

## 9. 常见问题排查

| 现象 | 可能原因 | 排查方法 |
|------|---------|---------|
| 查询版本无回复 | 波特率不匹配；设备未进入 OTA 解析状态 | 用 `--raw` 模式监听；确认设备主循环调用了 `ota_protocol_parse()` |
| 写入数据包返回 FAIL | 包号不连续（丢包或乱序） | 检查日志中包号是否从 0 开始连续递增 |
| 结束升级后回读 `magic=0xFFFFFFFF` | 升级标志地址超出芯片 Flash 容量；或该页被写保护 | 确认 `OTA_FLAG_ADDR` 在芯片实际 Flash 范围内；尝试换到其他页 |
| 升级完成后版本号未更新 | Bootloader 未重新编译；`ota_total_packets` 为 0 导致复制 0 字节 | 上电时查看 `[BL]` 调试输出，确认 `packets` 值正确 |
| 升级后设备无法启动 | App 区向量表无效；固件 bin 不是从 `0x08002000` 偏移编译的 | 确认 Keil5 中 App 项目的 IROM 起始地址为 `0x08002000` |
| 串口打开失败 "拒绝访问" | 串口被其他程序占用（如串口助手） | 关闭所有占用 COM 口的程序后重试 |
| 等待回复超时（过滤了 N 字节噪声） | printf 噪声中碰巧有 `0x55` 导致假帧头；或设备确实未回复 | 用 `--raw` 模式查看原始数据；确认设备端 `ota_send_response()` 被调用 |

> **重要提醒**：如果遇到 "API 返回成功但回读仍是 `0xFFFFFFFF`" 的情况，**第一反应应该检查目标地址是否超出芯片 Flash 容量**。GD32 的 FMC API 对越界地址不会报错，但数据不会落盘。
